# 墨洞「桌面端发现不到手机」根因排查与修复计划

## 已确认结论(逐行核对 + 单测)
`discovery.rs` / `service.rs` / `transport.rs` 里的发现协议、`611b27a`/`ac95af0` 两条反向发现修复、OnceLock 接线全部正确,且有单测覆盖(`a_one_way_announce_topology_still_discovers_both_directions`、`an_inbound_hint_beacons_a_peer_whose_announces_never_arrive`)。代码层面没有逻辑 bug。

## 真正卡点:失败不可观测
1. **部分失败被静默吞**(`discovery.rs:142-173`):UDP bind 失败 / mDNS 启动失败只会进 `startup_errors`,**只有两个都失败(返回 Err)时才发 `lan.status`**;若 UDP 挂了但 mDNS 活着,`start` 返回 `Ok(mDNS-only)`,UDP 失败被吞,用户看不到。这恰好对应"桌面端 UDP 41301 收不到包、退化为仅 mDNS"的场景 —— 而两条反向修复的 hint 分支都有 `let Some(socket) = socket.as_ref() else { continue }`,UDP 一挂就双双失效。
2. **项目没接任何日志**:`main.rs` 与全仓库都没有 `tracing`/`log` 订阅者,core 里 probe 超时、UDP bind 失败、mDNS 失败、收包失败的 `tracing::debug!/warn!/error!` 全被丢弃。开发者写两条修复时是盲调。

## 第一步实施:让失败可见(改 2 个文件,纯加可观测性)

### 1. `rust/apps/inkhole-desktop/Cargo.toml`
新增运行期依赖 `tracing-subscriber` 与 `tracing-appender`(版本对齐 workspace 的 `tracing`)。`tracing`、`dirs` 已存在。

### 2. `rust/apps/inkhole-desktop/src/main.rs`
在 `run()` 开头初始化日志:用 `tracing_appender::rolling::RollingFileAppender`(按天轮转)写到 `dirs::data_local_dir().join("InkHole").join("logs")`(Windows 下即 `%LOCALAPPDATA%\InkHole\logs\inkhole-<YYYY-MM-DD>.log`),叠加 `tracing_subscriber::fmt` 的 `NonBlocking` + `BufWriter` 层;默认 `INFO` 级别,读 `INKHOLE_LOG` 环境变量(`debug` 可下调)。保留 `WriterGuard`(存到 `DesktopState` 或 leak 保活)防止丢日志。
- release 是 `windows_subsystem = windows` 无控制台,故**必须写文件**。
- **不触碰任何 UI/布局/样式/交互/已验收 Windows 行为**,仅在 `run()` 起始加初始化,符合 AGENTS.md 冻结区。

### 3. `rust/crates/inkhole-core/src/discovery.rs`(核心库,只加 `tracing` 调用,不改逻辑)
把关键决策点抬到默认可见级别:
- **UDP bind 失败**(146)、**mDNS 启动失败**(161):加 `tracing::warn!`(带原始错误)—— 让"端口 41301 被占用 / mDNS 5353 被占"进日志(目前被吞)。
- **收到 announce**(455 附近):`tracing::info!`(sender `ip:port` / `instance_id` / `reply` / `bye`)。
- **probe 结果**:`apply_probe_outcome` 成功路径加 `info!`(含 target);失败路径(938 现为 `debug!`)抬到 `warn!`,带 target + 失败原因(超时/证书不匹配/连接拒绝/密钥)。
- **hint 信标**(387-409):发送、`known` 跳过、`rate-limited` 跳过三处加 `info!`;**611b27a 反向 announce**(578-581)发送加 `info!`(目标 `ip:port`)。

(桌面端 `handle_core_event` 已转发 `lan.status`,`desktop.rs` 无需改。)

## 第二步:复现 + 读日志(改完第一步请你复现一次,把 `inkhole-<日期>.log` 发我)
日志会直接落定到三选一:
- 出现 `UDP: <error>`(如 "address already in use") → 桌面端 UDP 41301 被占(僵尸进程/其它程序),退化为 mDNS-only → 第三步 A。
- 显示"收到手机 announce"但 `probe ... failed: <原因>` → 手机 QUIC 不可达/握手失败 → 第三步 B。
- 显示"没收到任何手机 announce"且 `mDNS: <error>` 或 mDNS 收不到 → Windows mDNS 失效 → 第三步 A 的 mDNS 兜底。

## 第三步:对症下药(依日志结论二选一,**动手前再向你确认**,且核心库改动先说明)
- **A(桌面端 UDP 收不到包 / mDNS 也挂)**:UDP 端口冲突则加启动检测 + 提示(引导关僵尸进程 / 放行防火墙);mDNS 因 5353 被系统占用则考虑 mDNS 端口兜底。可选健壮性(核心库、影响两端,先说明):用已依赖的 `if-addrs` 枚举本机 IPv4 接口,把每个接口的**定向广播地址**(`ip | !netmask`,如 `192.168.1.255`)连同 `255.255.255.255` 一起作为发现目标 —— 定向广播在 wifi↔wired 间比有限广播更易被转发。
- **B(手机 QUIC 不可达)**:依 probe 失败原因处理 —— 手机后台被系统挂起则强化前台服务保活 / 探测重试;announce 携带端口与实际监听不一致则修正。

## 范围与冻结区
- 第一步纯加可观测性(桌面端 `main.rs` 加日志初始化 + `Cargo.toml` 加两个依赖、core 加几条 `tracing` 调用),不改 Windows 已验收的 UI 布局/样式/交互,符合冻结区约束。
- 第三步若涉及核心库或桌面端行为改动,先向你说明再动手。
