# Cross-network transport

InkHole 2.0 has one transport implementation. The Rust `inkhole-core` crate
owns LAN discovery, direct transfer, one-time codes, and SSH relay sessions.
The desktop and mobile hosts only render state and forward JSON requests.

## Routes

1. LAN discovery announces a signed Ed25519 device record through UDP/mDNS.
   Peers are deduplicated by `instance_id` and may advertise multiple IP
   addresses. The QUIC listener defaults to a fixed port (41300, configurable)
   so firewalls and port-forwarding have a stable target; if the port is taken
   it falls back to an ephemeral one and reports it.
2. A direct connection uses Quinn QUIC. The peer certificate is pinned to the
   signed discovery fingerprint, then the optional shared secret authenticates
   the request with a BLAKE3 MAC.
3. If a direct route is unavailable, the sender can create a one-time code.
   Magic Wormhole provides PAKE rendezvous and an encrypted transit path; file
   bytes still use the InkHole streaming protocol and never land on the relay.
4. An SSH relay is an explicitly configured long-lived route. Host keys are
   checked against the configured `SHA256:` fingerprint before forwarding.
   Devices pair their relay identity with PAKE before the data channel starts.

## Name resolution and dialing (`net.rs`)

Every outbound TCP dial (rendezvous WebSocket, transit relay, transit hints,
SSH) goes through `net::dial_host_port`, which fixes two field-observed
failures:

- **Blackholed system DNS.** Some networks resolve international names slowly
  or not at all through the system resolver. The system resolver and a direct
  public-DNS query (AliDNS / DNSPod / Google over UDP:53, a tiny built-in
  codec, no new dependency) race; the system resolver gets a 300ms head start
  (it is fastest for healthy and `.local`/private names), and public DNS takes
  over the instant the system one stalls.
- **Blackholed IPv6 first.** `getaddrinfo` often returns AAAA first (RFC 6724)
  while a network has no working IPv6 route, so serial dialing burns the whole
  timeout on a dead address. Resolved addresses are sorted IPv4-first and
  dialed with a 300ms staggered race (Happy Eyeballs), so the first address
  that completes its handshake wins.

## Transit path selection and throughput

The one-time code path builds its candidate list from both address families:
the sender binds IPv4 and best-effort IPv6 listeners and advertises LAN IPv4
plus global-unicast/ULA IPv6 addresses, so two peers that **both** have public
IPv6 connect directly across networks with no relay. The receiver dials every
hint in parallel and the first authenticated stream wins; the relay dial is
delayed by 400ms so a reachable direct path always beats the relay. Rendezvous
commands that do not depend on a prior response are pipelined
(`bind`+`allocate`, `bind`+`claim`) to cut serial round-trips on high-latency
links.

QUIC uses MTU discovery starting from the spec-safe 1200-byte floor rather than
a hardcoded Ethernet MTU: Tailscale (1280) and other VPN tunnels have a path
MTU below Ethernet, and starting at 1452 would blackhole oversized handshake
packets and collapse the congestion window. Discovery probes back up to 1452
within a few round trips, so LAN is unaffected.

When the relay is the only viable path, QUIC datagrams are framed into
encrypted records over the transit TCP stream. The tunnel buffers up to 1024
datagrams and drains them in batches through a single buffered write and
flush, so QUIC bursts are smoothed instead of dropped and per-datagram
syscall overhead stays flat. The SSH relay channel uses a 16MB flow-control
window sized to the QUIC send window.

## Cross-network reachability (the relay is the weak link)

Pairing (rendezvous) and data transfer (transit) are separate hops. Pairing
succeeds cross-network as long as both peers reach the rendezvous server over
WSS/443. Data transfer, when neither direct LAN nor direct IPv6 is available,
**must** flow through a transit relay that both peers can reach on the same
port.

The defaults (`relay.magic-wormhole.io`, `transit.magic-wormhole.io:4001`) are
the free public Magic Wormhole servers in the US. They are frequently slow or
unreachable from some networks — notably Chinese cellular, where the relay's
non-standard 4001 port to a foreign IP is often blocked — so cross-network data
transfer can fail even when pairing succeeds. Both endpoints are configurable
in app settings; self-hosting a relay reachable from both peers (see
[自建短码服务器.md](自建短码服务器.md)) makes the one-time-code path reliably
cross-network and moves pairing latency and relay bandwidth onto your own
server. For two devices you own, a Tailscale fixed address (added as a manual
peer) is direct QUIC with no relay at all.

## File protocol

Every file and folder is streamed in bounded frames. A folder begins with a
signed, sorted manifest that includes relative paths, directory entries, file
sizes, modification times, and a BLAKE3 digest. Receivers reject traversal,
duplicate, symlink, and type-confusion entries before creating any output.

Data is written to a temporary path and atomically committed only after the
final BLAKE3 digest and completion receipt match. Each transfer has a durable
checkpoint, a cancellation token, and a resumable offset. A cancelled or
interrupted transfer cannot be reported as successful.

## JSON service boundary

The host-facing methods are implemented by `JsonService`:

```text
lan.start / lan.refresh / lan.send / lan.send.cancel / lan.stop
wormhole.create / wormhole.join.start / wormhole.accept / wormhole.reject
ssh.listen / ssh.pair.create / ssh.pair.join / session.cancel
```

Desktop calls the service directly from Tauri. Flutter keeps one FFI service
handle in a dedicated isolate and polls the same event queue. No Go, Python,
Kotlin, gomobile, or loopback sidecar is part of the 2.0 protocol.
